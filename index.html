왜 어려웠나

제조사가 펌웨어를 배포하지 않아 보드의 SPI 플래시에서 직접 덤프해야 했습니다. 디버깅 포트도 막혀 있어서 기기 한 대로는 같은 실험을 반복하기 어려웠고, 잘못 건드리면 기기를 못 쓰게 될 위험도 있었습니다. 자료도 추출·정적 분석·동적 분석이 따로 흩어져 있어서 처음부터 끝까지 이어지는 흐름을 직접 만들어야 했습니다.

이미지 분해 — 어디까지가 커널이고 어디부터 파일시스템인가

binwalk로 시그니처 오프셋을 확인해 Bootloader·Kernel·squashfs 영역을 잘라내고, FMK로 RootFS를 풀어 디렉터리 구조와 init 스크립트를 확보했습니다.

커널 — 원본 커널은 QEMU에서 뜨지 않았다

원본 커널은 실제 SoC 보드 전용이라 QEMU 가상 보드에서 부팅되지 않았습니다. → 펌웨어와 같은 버전대의 커널을 QEMU MIPS(malta)용으로 크로스 빌드하고, 복원한 RootFS를 붙여 부팅에 성공했습니다.

하드웨어 의존성 — 메인 프로세스가 장치를 못 찾고 종료

부팅 후 메인 바이너리가 카메라·GPIO/NVRAM 같은 실제 장치를 찾지 못해 바로 종료됐습니다. → Ghidra로 종료 지점이 되는 함수를 찾고, LD_PRELOAD로 해당 함수를 정상 값을 돌려주는 함수로 대체해 프로세스가 계속 동작하게 만들었습니다.

정리 — 다른 사람이 따라 할 수 있게

추출부터 동적 분석까지를 4개 챕터로 문서화해 GitHub에 공개했습니다. 담당 챕터: 파일 시스템 구성 / 동적 분석 진행

Ghidra 디컴파일 화면 + LD_PRELOAD 후킹 코드 (나란히)“이 함수에서 종료 → 이렇게 대체”가 한눈에 보이게 주석 표시

배운 것

에뮬레이션이 실패하는 이유는 대부분 코드가 아니라 하드웨어 주변장치에 대한 의존성이었습니다. 무엇을 흉내 내고 무엇을 후킹으로 우회할지 판단하는 것, 즉 대상의 구조를 먼저 이해하는 것이 동적 분석의 핵심이라는 걸 배웠습니다.

차량보안진단에서는

제어기(ECU)·IVI·텔레매틱스 단말 진단도 펌웨어 확보 → 구조 복원 → 에뮬레이션 기반 동적 테스트라는 같은 흐름을 따릅니다. 실차나 실물 제어기가 한정된 상황에서도 취약점을 재현하고 검증할 수 있는 환경을 직접 만들 수 있다는 점이 이 경험의 의미라고 생각합니다. ISO/SAE 21434에서 요구하는 검증 단계 침투 테스트의 출발점이기도 합니다.

다음에 해보고 싶은 것

구축한 환경 위에서 AFL++ QEMU 모드로 네트워크 데몬을 퍼징해, 환경 구축을 넘어 실제 취약점 발견까지 이어가 보고 싶습니다.

ChipWhisperer로 암호 연산 중 전력 파형을 수집하고, DPA·CPA 공격을 C로 직접 구현해 AES와 ARIA의 비밀키를 복구했습니다.

기간2024.03 – 2025.02소속PEPSI 부채널 분석 동아리담당파형 수집 · 공격 코드 구현 · 경진대회 문제 풀이

왜 시작했나

AES는 수학적으로 깨지지 않았지만, 그 AES를 실행하는 칩은 연산할 때마다 데이터에 따라 미세하게 다른 전력을 씁니다. 공격자가 기기를 손에 쥘 수 있다면 이 차이만으로 키를 알아낼 수 있다는 점이 흥미로웠고, 직접 성공시켜 봐야 이 위협이 얼마나 현실적인지 판단할 수 있다고 생각했습니다.

무엇을 다르게 했나

ChipWhisperer가 제공하는 분석 예제를 실행하는 데서 멈추지 않고, 공격 로직 전체를 C로 직접 구현했습니다. 같은 파형으로 DPA와 CPA를 모두 돌려 필요한 파형 수를 비교했고, 구조가 다른 ARIA에도 적용해 봤습니다.

파형 수집부터 키 판별까지 공격 파이프라인 전체를 직접 구현했습니다

대상AES-128 · ARIA-128, 1라운드 S-box 출력장비ChipWhisperer Lite + STM32F3 타깃

파형이 조금씩 밀려 상관 피크가 흐려졌다

수집 시점마다 파형이 미세하게 어긋나 정답 키의 상관계수가 다른 후보에 묻혔습니다. → 기준 파형과의 상호상관으로 정렬한 뒤, S-box 연산 구간만 잘라 분석해 정답 키가 뚜렷하게 분리되도록 했습니다.

파형 수가 늘수록 계산이 느려졌다

키 후보 256개 × 파형 수 × 샘플 수만큼 상관계수를 계산해야 했습니다. → 합·제곱합을 누적하는 방식으로 파형을 한 번만 읽고 계산하도록 바꿔 x배 빨라졌습니다.

AES용 모델을 ARIA에 그대로 쓸 수 없었다

ARIA는 라운드마다 다른 S-box를 쓰는 등 구조가 달라 공격 지점을 다시 잡아야 했습니다. → 알고리즘 명세를 보고 첫 라운드 S-box 출력을 공격 지점으로 정해 모델을 분리 구현했습니다.

실제 수집한 AES 전력 파형 1장10라운드 반복 구간에 라벨

배운 것

ARIA를 공격하면서 대상의 내부 구조를 정확히 알아야 공격 지점이 보인다는 것을 체감했습니다. 또 “안전한 알고리즘”과 “안전한 구현”은 다르다는 것, 그래서 보안은 설계 문서가 아니라 실물에서 검증해야 한다는 것을 배웠습니다.

디지털키·스마트키, HSM이 탑재된 제어기처럼 공격자가 물리적으로 접근할 수 있는 장치의 키 보호 수준을 평가할 때 바로 쓰이는 관점입니다. 직접 공격에 필요한 장비·시간·파형 수를 겪어 봤기 때문에, ISO/SAE 21434 TARA의 공격 가능성(Attack Feasibility)을 근거를 갖고 판단할 수 있습니다.

만든 것

라즈베리파이 두 대 사이를 레이저와 CdS 센서로 연결해 데이터를 주고받는 시스템입니다. 처음엔 비트만 그냥 보냈더니 데이터가 계속 깨졌습니다. Linux 사용자 공간에서는 μs 단위 타이밍이 보장되지 않고, 센서 반응도 느려 비트를 읽는 시점이 계속 어긋났기 때문입니다.

해결한 방법

타이밍은 Start bit 이후 1.5T 지점에서 비트 중앙을 샘플링하고, 송신은 pigpio DMA 파형으로 OS 스케줄링 영향을 없앴습니다. 그래도 남는 오류는 [STX][DATA][CHECKSUM][ETX] 프레임과 ACK/NACK·타임아웃 재전송으로 잡았습니다.

보안 관점으로 다시 보니

체크섬은 우연한 오류는 잡지만, 공격자가 데이터를 바꾸고 체크섬을 다시 계산하면 막을 수 없습니다. 지난 프레임을 그대로 다시 보내도 구분할 방법이 없습니다. Movisec에서 Wireshark로 분석했던 재전송(Replay) 공격이 바로 이 지점이었고, 차량에서는 이를 AUTOSAR SecOC(MAC + Freshness Value)로 막는다는 것까지 연결해 이해했습니다.
